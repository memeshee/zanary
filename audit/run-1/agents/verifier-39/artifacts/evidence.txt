3. Affected principal / impact — as written, not strengthened:
   This is the local regtest harness tool the operator runs on its own throwaway wallet; the
   definition file is caller-supplied. Dev build: abort before any wallet/node work (no diagnostic
   naming the invoice). Release build: wrong total, run proceeds, later per-amount checks
   (ops.rs:912/983) or the node error stop it. No funds/keys/authority exposure, no memory-safety
   or privilege claim — the record's low/low/low severity and its "nothing stronger than the claim
   was observed" confidence statement are consistent with what I reproduced.

4. Remediation — sound: validate amounts (1..=MAX_MONEY) and accumulate the total with checked_add
   in run_recording beside the existing checks (the last trusted point where the definition enters),
   then have the three sum sites consume the validated total. That enforces the invariant where the
   untrusted values first arrive rather than moving trust downstream. The proposed snippet's
   `total_zat` consumption covers the three flow.rs sites; no other flow.rs sum exists (see 1).
