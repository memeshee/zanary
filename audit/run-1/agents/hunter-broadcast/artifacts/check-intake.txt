--- what this settles ---
1. A merchant-supplied invoice whose `receiver` is a Sapling address (zregtestsapling1...) or a
   unified address with a Sapling receiver and no Orchard receiver is ACCEPTED by the payer's
   payment intake and reaches the wallet layer inside the target's own function
   ops::propose_shielded_payments ("Must scan blocks first" — the stub wallet, not any check on
   this path, is what stops it). Same result with the invoice memo and with an empty memo.
2. The guard every other payment path calls — ops::required_policy_for_recipient + ops::check_policy
   (ops.rs:1019-1020 for `pay`, ops.rs:563-566 for `anchor`, flow.rs:633-634 and flow.rs:826-827
   for the flow runner) — REFUSES exactly that recipient under FullPrivacy: "would reveal the
   amount (Orchard -> Sapling pool crossing)". payer.rs has 0 occurrences of either function
   (counted from the compiled source) and writes pool_in/pool_out/kind/policy as literals without
   ever reading the proposal back (proposal.steps / payment_pools appear nowhere in payer.rs).
3. A bare transparent receiver never reaches that point: zip321's memo rule refuses it inside the
   target's own intake ("Cannot send a memo to a transparent recipient address"), with the invoice
   memo and with an empty memo. The reachable divergence is therefore limited to shielded
   (Sapling) receivers.
4. payer::decide admits invoices the payment loop cannot execute: with the documented empty
   allowlist and an amount inside cap and budget, an invoice whose receiver is "not-an-address" is
   decided allowed=true and then Address::decode returns NONE (payer.rs:298 aborts, after any
   earlier invoice was already broadcast); an invoice whose memo is 600 bytes is likewise decided
   allowed=true and rejected by MemoBytes::from_bytes (payer.rs:304-305).
5. The payer's intake deserializes the invoice JSON directly (payer.rs:515-516) while
   Invoice::from_path (the `pay --invoice` path) cross-checks the file against its own ZIP-321 URI:
   an invoice whose URI pays the account's Orchard UA but whose `receiver` says Sapling is accepted
   by the payer and refused by the CLI path ("refusing an invoice that disagrees with itself").

--- what this does NOT settle ---
The proposal and the broadcast itself. Building a proposal needs a wallet holding a spendable
Orchard note; the sandbox has none (zcash_client_backend's test-wallet framework needs the
`test-dependencies` feature set -> proptest/ambassador/assert_matches, none of which are in the
read-only offline registry cache, and no network is permitted), and the only funded wallet lives
in the regtest rig, which is out of bounds for hunters. So the last step — the wallet builds the
Sapling output, the indexer accepts the transaction, and the run's report then reads
policy-downgrade PASS — is established by source (zcash_client_backend 0.24.0,
src/data_api/wallet/input_selection.rs:966-968 delivers Address::Sapling through a Sapling output,
and 999-1003 does the same for a unified address with a Sapling receiver and no Orchard receiver)
and needs owner-side execution on the rig to be observed.
