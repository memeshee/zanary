## 1. The bounded payer writes every payment record from literals (Orchard -> Orchard, Shielded, FullPrivacy) and never applies the recipient-policy guard, so a payment whose transaction crosses a shielded pool boundary (a Sapling receiver) would be recorded and scored as a same-pool, fully-shielded, FullPrivacy payment

`crates/probe/src/payer.rs:payment-record-pool-legs-and-policy-are-constants-not-derived-from-the-built-transaction`

payer::run pays each invoice it admitted through ops::propose_shielded_payment / ops::build_sign_broadcast and then records the payment at payer.rs:339-362, where pool_in: Pool::Orchard (349), pool_out: Pool::Orchard (350), kind: PaymentKind::Shielded (351) and policy: Some("FullPrivacy") (352) are constants: none is derived from the proposal or the transaction, and payer.rs never reads the proposal back (0 occurrences of proposal.steps / payment_pools / any transaction decryption, against ops.rs:1076-1126 where `pay` decrypts the mined transaction). observation/src/lib.rs:28-30 defines PaymentKind::Shielded as "shielded source and shielded destination, same pool" and 56-60 defines pool_out as the payment's destination pool and `policy` as "the privacy policy argument the flow passed to its wallet layer, verbatim" - the payer passes no such argument. This path also never calls ops::required_policy_for_recipient + ops::check_policy (payer.rs: 0 call sites; every other payment path does: ops.rs:563-566, 777, 1019-1020; flow.rs:633-634, 826-827), and ops::propose_shielded_payments (payer.rs:306-307 -> ops.rs:900-961) applies SpendPolicy::shielded_pools([Orchard]) to input sources only (zcash_client_backend 0.24.0 input_selection.rs:476-489, 966-968, 999-1003). The recipient comes from the merchant's invoice file, deserialized directly (payer.rs:495-519, no ZIP-321 cross-check unlike flow.rs:1740-1768), and decide only string-compares it against the grant allowlist (payer.rs:100); an empty or absent allowlist admits every receiver (printed at payer.rs:222-224). The record then decides every verdict derived from it: policy-downgrade (Severity::Disqualifying) computes its explicit signal from Payment.policy (76-89; "FullPrivacy" matches no downgrade fragment) and its implicit signal from pool_in (shielded) plus pool_out in {Transparent, CrossPool} (92-101), so the payer's constant record makes it PASS - reproduced with zanary_properties::evaluate() in the sandbox, where the fixtures' honest cross-pool record (fixtures.rs:243-246) FAILs as a positive control. ## 2. Bounded payer queues an unbounded number of payments: the grant bounds the sum of amounts, not the count of heavy per-invoice work

`probe/payer.rs:run:unbounded-payment-count`

run() appends every invoice decide() allows to to_pay with no cardinality cap (payer.rs:249-260) and then pays them one at a time (payer.rs:291-309). Each queued entry costs fixed heavy work: a proposal (ops.rs:884-891), an Orchard build/prove/sign and broadcast through the indexer (ops.rs:360-428), then 11 mined blocks plus a wallet resync (payer.rs:309 -> ops.rs:433-451; CONFIRM_BLOCKS = 11 at ops.rs:59). The grant bounds only each amount and the running sum of amount_zat (payer.rs:110-128), so zero-amount invoices never consume the 50,000,000-zat default budget (payer.rs:64-66) and one-zat invoices fit up to 50,000,000 payments, while the attacker's per-payment input is one small JSON file (~140 B). Independently reproduced from a fresh build of the pinned revision inside the sandbox: 5,000 zero-amount invoices were all read, decided ALLOW and queued in one run ('invoices : 5000', 5,000 ALLOW lines, ~1 s), and a 300-file one-zat run with budget 150 admitted exactly 150 (the sum-of-amounts budget was the only count-limiting check). The run then requires the harness node (payer.rs:275-276) and stops with 'Connection refused' in --network=none, so the payment work itself, its per-payment cost and the effect of N sequential payments on the shared regtest node are owner-rig observations this audit cannot make.

**Claimed root cause.** No bound on the number of invoices accepted into payment work: run() queues every allowed invoice (payer.rs:249-260) and pays them in a serial loop with no per-run payment-count cap (payer.rs:291-309); the grant bounds only amounts (payer.rs:110-128), and each queued entry is fixed heavy work (proposal, Orchard proof, broadcast, 11 mined blocks + wallet resync; ops.rs:59, 360-428, 433-451).

**Trace**

1. *entrypoint* — `crates/probe/src/payer.rs:150` (payer::run): --invoices directory supplies the invoice count; load_invoices (payer.rs:495-520) collects every *.json entry, so the count is caller/merchant-chosen
1. *propagation* — `crates/probe/src/payer.rs:250` (payer::run): decide() is the only gate: per-payment cap (110-117) and sum-of-amounts budget (119-128) are amount checks only
1. *propagation* — `crates/probe/src/payer.rs:259` (payer::run): every ALLOWed invoice is appended to to_pay with no cardinality check (loop 249-260)
1. *propagation* — `crates/probe/src/payer.rs:307` (payer::run): payment loop (291-309) is serial over the queue: propose_shielded_payment (306-307), build_sign_broadcast (308), then mine_and_resync(CONFIRM_BLOCKS) (309) per queued entry; no payment-count bound
1. *sink* — `crates/probe/src/ops.rs:436` (ops::mine_and_resync (called per payment from payer.rs:309)): node.generate(CONFIRM_BLOCKS=11) mines 11 blocks on the harness node then core::sync_wallet re-syncs (ops.rs:433-451) before the next payment starts - serial heavy work per tiny attacker file

**Verified evidence**
